## 4. ID proposal

### 4.1 Status
`DDPD IDs: Current Problems and Proposed Fix` was drafted in this workspace for Zach. It lists 7 problems and proposes one format per type, stable readable keys, no folder path in IDs, and a "Validates" field on tests instead of criteria inside test IDs. **The direction is good. Make the changes in 4.2 before sending.**

### 4.2 Suggested changes before sending

1. **Rename the product example.** `PDID-MAILROOM` is easy to confuse with the **Mailroom Intake** capability (SDS's hosted mailroom). Use `PDID-DIGITALMAILROOM` or `PDID-DMR` instead.
2. **Add an ID for customer associates.** CENCORP has plans or lines of business under it (Centene, WellCare, Fidelis, Health Net). Proposal: `CLID-CENCORP-<ASSOC>`, for example `CLID-CENCORP-FIDELIS`. Confirm the associate codes against the code before using them.
3. **Add an ID for customer variations.** Not every customer difference is a change request. Many are just configuration or code overrides of the base (BCS). Proposal: `VRID-<CODE>-<nnn>`, for example `VRID-CENCORP-002`. A variation can point to the change request that caused it, if there is one.
4. **Say where test IDs live in code.** QuickClaim tests are JUnit 5, so the "Validates" values go in `@Tag` values. JUnit tags cannot contain spaces or the characters `, ( ) & | !`. The proposed IDs only use letters, digits, and hyphens, so they are valid. State this in the proposal.
5. **Say that keys are unique across products, capabilities, features, and workflows.** The proposal says features and workflows. Extend it to all keyed types so `TCID-<KEY>` can never be ambiguous.
6. **Add a "termination" field note.** The termination search only works if every customer-specific item carries a `Client:` or `Change request:` field. Make that a required field on features, stories, and variations that exist for one customer.

### 4.3 Change request chain (Zach's 10/27 guidance, tie it to the IDs)

- A change request (`CRID-<CODE>-<nnn>`) lives in the client folder.
- It has an **outcome type:** customer-only, enhancement, or product change.
- It lists everything it created or changed (features, stories, variations, config).
- Every item it created carries `Change request: CRID-...` and is marked **contractual**, so agents do not change or delete it freely.
- Trace chain: client > change request > feature or story > acceptance criteria > tests.
- CENCORP may not have formal change requests yet. Implementation-specific needs still count. Zach's example: CENCORP has documents that must be labeled a certain way, used only by them. Record that as a change request or variation so it can be found and removed later.
